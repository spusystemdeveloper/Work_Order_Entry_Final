# Work Order Entry V8

VB.NET RMS add-ins for Work Order Entry and Order Processing Queueing.

## Application deployment and printing

Build `Work Order Entry.sln` in Release / x86. Deploy the **whole**
`Work Order Entry/bin/Release` folder, including these matching ReportViewer DLLs:
`Microsoft.ReportViewer.Common.dll`, `Microsoft.ReportViewer.WinForms.dll`,
`Microsoft.ReportViewer.ProcessingObjectModel.dll`,
`Microsoft.ReportViewer.DataVisualization.dll`, and `Microsoft.ReportViewer.Design.dll`.
They come from the project's ReportViewer package `150.1652.0` and must remain
beside `Work Order Entry_V8.exe`. Other managed dependencies remain embedded.
Copying only the EXE is insufficient for this build; ReportViewer 2005 is not a
replacement for the bundled version. No separate ReportViewer install is needed.

On an existing unit, retain its store-specific `Work Order Entry_V8.exe.config`
when replacing the EXE and DLLs. On a new unit, review the configuration for the
intended store. Application packaging does not deploy database migrations.

Start the EXE from the updated folder and update any Desktop shortcut to that
location. A separate old Desktop EXE will continue running the old code. An import
error naming `ExcelDataSetConfiguration.set_ConfigureDataTable` can occur with
the legacy embedded-DLL loader when it loads ExcelDataReader more than once.
Deploy the current complete package; do not mix old EXEs or Excel DLLs into it.

Verify the Release package with
`Database Components/Tests/Packaging_CleanFolder_Test.ps1`: it reads synthetic
CSV/XLSX files and renders the actual embedded WO/pick-list reports to PDFs in a
clean folder without an app config or installed ReportViewer 15 dependency.
It does not open the real app, access SQL, or send a physical print job. See
[the testing guide](UNIT_TEST_GUIDE.md). A normal unit test can miss packaging failures.

## Database deployment

Use the separate [Work Order Database Updater](Database%20Updater/README.md)
to review and apply selected migrations, function/object updates, or performance
indexes. Build the solution in Release / x86 and copy the updater's whole output
folder. It runs without Windows administrator elevation and uses an explicitly
selected SQL database/login. Changes are transactional and recorded with file
hashes. Future reviewed SQL fixes can be added through the tool.

Follow the [updater user guide](Database%20Updater/USER_GUIDE.md) for workstation
setup, importing SQL, creating/updating functions, and adding package entries.
The tool also includes an offline **Help / instructions...** button and example
SQL files for use on a disposable restore.

The application-referenced database objects are stored as individual,
idempotent SQL files with separate DVO and GSC definitions where the live
branches differ:

- `Database Components/Deployment/README.md` - deployment workflow and known
  blockers.
- `Database Components/Deployment/Manifest.csv` - all 49 audited objects,
  types, requirements, hashes, and placement.
- `Database Components/Deployment/Comparison/OBJECT_DIFFERENCES.md` -
  branch comparison.
- `Database Components/Deployment/Deploy_DVO_STORE_DB.sql` and
  `Deploy_GSC_STORE_DB.sql` - guarded SQLCMD drivers.
- `Database Components/Deployment/Objects/PortableBaseline` - seven required
  local-database definitions for GSC and future RMS branches that do not
  already have approved branch-specific versions.
- `Database Components/Migrations/Upgrade_GSC_STORE_DB_For_WorkOrderEntry.sql` -
  standalone, idempotent SQL migration script ready to execute in SSMS against
  `GSC_STORE_DB`.

The package was generated by read-only inspection. It does not modify either
live database. Always test the matching branch driver against a disposable
database restore before production deployment.

## Unit tests

For stores missing the item-code lookup index, see
`Database Components/Migrations/Improve_WorkOrder_ItemLookup.sql` and
`Database Components/Migrations/WORKORDER_ITEM_LOOKUP_GUIDE.md`. This optional
database optimization preserves the application rules and is not automatically
included in the branch deployment drivers.

The test project contains 101 database-free unit tests for price levels,
print-template selection, import-file routing, branch validation,
senior-citizen tags, VAT, tax exemption, non-taxable pricing, queue order-age
rules, error logging, edit-conflict validation, ready notifications, and customer
acceptance of warehouse shortages and loading-overlay scope handling.
All 101 passed on October 14, 2026.

Run the unit tests from the repository root with:

```powershell
.\Run-UnitTests.ps1
```

See `UNIT_TEST_GUIDE.md` for a plain-language explanation of what each test
does and what still requires integration testing.

## Branch database lock

Branch selection is disabled by default. Configure it in the
password-protected **Settings** form under **Branch Functions**:

- Clear **Allow Branch Selection** and enter the **Assigned Database**
  (for example `DVO_STORE_DB` or `GSC_STORE_DB`) to lock the installation.
- Select **Allow Branch Selection** to show the store database selector
  during startup.
- Click **Save**, close the application, and start it again.

In locked mode, the application uses the local RMS Store Operations registry
connection and stops before login if its database does not match the assigned
database. The controls save `BranchSelectionEnabled` and
`ExpectedDatabaseName` in the deployed application configuration.

## Order tools

Work Order Entry now includes an order history window, a ready-for-invoicing
notification, and protection against saving or cancelling a stale recalled order.
Warehouse shortage alerts also appear automatically in the status bar; click
the alert or **Order actions → Warehouse shortages...** to open an affected order.
The list supports local search, picker selection, new/changed and zero-found
filters, result counts, and Clear filters without extra database queries.
Cashiers can accept a positive warehouse shortage after customer agreement;
saving reduces the quantity, amounts, and reserved stock together, preserves the
picker, and records the decision. RMS stock on hand is unchanged.
Open history or reload an order from **Order actions** in the bottom status bar.
History and shortage acceptance require the optional `Enable_WorkOrder_History.sql` migration;
`Prepare_WorkOrder_Edit_Checks.sql` supplies lookup indexes recommended for
large queues. See `ORDER_TOOLS_GUIDE.md` for use, deployment, and verification.
